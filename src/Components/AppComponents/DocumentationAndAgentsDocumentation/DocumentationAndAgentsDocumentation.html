Documentation & AGENTS.md

How Slice projects document components, categories, events and decisions, and how coding agents read that documentation.

Slice projects ship documentation as part of the project, not as a follow-up. The goal is simple: an agent or a new teammate should know what a category is for, which component owns a behavior, which events cross a boundary, and what changed — without guessing.

What slice init creates

A fresh project gets the documentation scaffold next to the code:

src/markdown/ is not part of an app project. That folder belongs to the Slice.js Components and Slice.js Docs sites, which generate pages from Markdown. Apps document the module next to the module.

Read order for agents

Every coding agent should read, in this order:

  1. AGENTS.md at the project root.
  2. The nearest src/Components/<Category>/AGENTS.md.
  3. The component's README.md when changing its API, behavior or events.
  4. docs/events/ when changing an event contract.
  5. The relevant design/decision note, if the project keeps one.

AGENTS.md is an open Markdown format used by Codex, OpenCode, Cursor, Gemini CLI, Aider, Jules, Factory, Devin, VS Code/Copilot, Windsurf, Amp and others. Claude Code reads it directly on current versions; CLAUDE.md imports it for older versions. A direct user instruction wins over all of them.

Root AGENTS.md

The root file is a router. It answers:

  • what this project is;
  • which commands to run;
  • which categories exist and where their guides live;
  • where component docs, event docs and changelogs live;
  • what “done” includes.

Category AGENTS.md

Every category in sliceConfig.paths.components has a guide. It explains the category, not just the files.

Visual and Service

These are the registry categories. slice get installs components there. Their guide states the rule:

  • a registry component is not edited by hand;
  • its authoritative docs are slice docs / MCP;
  • a local component added to the same category is app-owned and documents its own README.md.

App categories

Custom categories such as Domain, Core, Providers or AppComponents are app-owned. Their guide should cover:

  • what belongs here and what does not;
  • the local conventions and invariants;
  • the component inventory;
  • which events cross the boundary;
  • gotchas learned during implementation.

A good guide is documentation, not boilerplate. “Components go here” is not enough.

Component README.md

An app-owned component documents itself next to its code:

  • purpose and when not to use it;
  • public props/API;
  • events emitted or listened to, with namespaces;
  • a minimal usage example;
  • lifecycle or singleton constraints;
  • gotchas;
  • a link to the category changelog if the project uses one.

Registry components do not get a local copy of their docs. That would go stale; link to slice docs get <component> instead.

Event documentation

Rules:

  • Event names are namespace:action.
  • Each namespace page lists payload, emitters, listeners, category and file:line.
  • index.md lists declared-but-unused events, used-but-undeclared events, names without a namespace, and dynamic sites.
  • The scanner excludes *.spec.js, *.test.js, *.generated.js, src/public/ and src/bundles/.

Changelog is optional

The scaffold does not force a changelog. If the project uses one:

  • CHANGELOG.md root for release-level changes;
  • src/Components/<Category>/CHANGELOG.md for category-level changes;
  • per-component changelogs only for components with their own release history.

A feature does not create a folder. It adds an entry to the changelog that already exists. If the project has no changelog, do not invent one unless the user asks.

What to update for each change

If none apply, say “No docs impact” and why. A test-only change or an internal refactor with no public behavior is a valid reason.

Library docs are different

slicejs-components and slicejs_docs are documentation sites. Their Markdown source lives in src/markdown/ or markdown/ and their parsers generate the pages. That pipeline does not apply to apps.

When working in those repositories:

  • edit the Markdown source, never the generated pages;
  • run the repo's docs generator;
  • regenerate the component agent manifest and OG/SEO artifacts when the page is public;
  • update the framework docs and the shared skill when guidance changes.

Why this helps agents

  • The root guide is small and points to the nearest category.
  • The category guide explains the boundary and links the component docs.
  • The component README explains the contract and gotchas.
  • The event catalog is generated from the actual call sites, so it cannot silently drift.
  • slice docs check catches stale generated docs before a build or PR.

The result is documentation that is local, discoverable and current — not a second README nobody reads.
