Slice Routing

Overview

Slice Router handles client-side navigation, route parameters, nested routes, and route containers. It auto-starts shortly after initialization, but you should call start() manually when you use guards to ensure your guard logic runs before the first navigation.

Routing is driven by a routes.js file and a runtime router available at slice.router.

Path matching is case-insensitive: /About resolves to a route declared as /about. This applies to both static and ${param} routes, and to MultiRoute containers. Captured parameter values keep their original case (for example ${id} in /User/AB12 is AB12).

Router API

slice.path and slice.href(path) are the shortcuts at the slice level: components use those instead of window.location.pathname and of a per-component helper.

The product name belongs in the config, not in every route:

A route with metadata: { titleKey: 'pricing.title' } renders Precios · Acme in Spanish and Pricing · Acme in English. titlePrefix is the mirror ("Acme · "), and both compose as prefix + title + suffix; only one, both or neither are valid. The separator is part of the string.

titleKey wins over title when the translator is enabled. With it disabled the key is shown as the title and the router logs one warning per key, so an untranslated page is visible instead of silently wrong. The server reads the same router.titlePrefix/titleSuffix when it prerenders, so the tab title does not change after hydration.

It only writes what the route declares: a route without a title keeps whatever the server sent, so a prerendered page is never downgraded. canonical and robots are never written from the client — crawlers do not run JavaScript. A router:change listener still wins, because the metadata is applied before the event. Opt out with router.updateTitles: false in sliceConfig.json.

Basic Navigation

Route Containers

Slice provides two route container components:

  • slice-route for a single path
  • slice-multi-route for a list of routes

They cache components and call update() when a cached component is reused.

routes.js is the single source of truth for the Router. Containers do not register their paths with the Router — they only choose which component to show for the current URL. So every path a Route/MultiRoute can show must also exist in routes.js (in the App Shell pattern it maps to the shell). Otherwise a direct load, refresh, or deep-link to that URL resolves before the container mounts and falls through to /404.

Guards

Route Change Events

The router emits router:change once per navigation, after the new route has been rendered. How you listen depends on whether EventManager is enabled — it's one or the other, never both:

  • events.enabled: true → it goes through EventManager (slice.events).
  • events.enabled: false → it dispatches a CustomEvent of the same name on window instead.

Either way the payload is { to, from }, where each is a route object shaped { path, component, params, query, metadata }:

When events are enabled, router:change is auto-declared in the [Event Registry](/Documentation/Structural/EventRegistry), so you can subscribe without register()-ing it first.

Prefer the event's to payload over reading slice.router.activeRoute inside the handler. activeRoute does reflect the new route by the time router:change fires, but the payload is the guaranteed source and keeps your listener decoupled from router internals. If you only need the current URL, window.location.pathname is always trustworthy the instant the event fires.

Best Practices

Call start() after registering guards to avoid missing the first navigation.
Use metadata flags to keep guard logic declarative and centralized.

Gotchas

navigate() is async. Await it when you depend on the next route being ready.
Dynamic params use ${param} syntax, not :param.
