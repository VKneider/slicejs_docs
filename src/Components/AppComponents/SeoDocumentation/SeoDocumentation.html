SEO and Share Cards

A Slice app is a SPA: the browser gets one App/index.html and the router swaps the view. Left alone that means one <title> for every route, no canonical, a 200 for URLs that do not exist, and a link preview that looks the same everywhere. The framework fixes the mechanics; you provide the content.

The manifest: seo.json

One file, with one entry per page. It can live at the project root (hand-written) or inside public/ — src/public/seo.json, which is what a generated pipeline writes. The server and the slice seo commands check the root first, then public/:

defaults are inherited by every route, so a title suffix or a site-wide card is written once.

Routes with parameters

Use the router's syntax. A pattern provides the metadata for every instance, and the canonical is always the real path:

/producto/42 gets that title and origin + /producto/42 as its canonical. A pattern cannot be enumerated, so it never enters the sitemap. A title built from the parameter needs the route's own metadata in routes.js and is not part of this version.

Enabling it

At startup the server reads the manifest, imports routes.js to know which paths are pages, renders each one once (head injected into the shell, gzip + brotli + ETag precomputed) and keeps them in memory. A request is a lookup and a write.

The origin, and why it is not read from the request

The head is prerendered once, so the origin has to be known at startup. It is resolved in this order:

  1. SLICE_ORIGIN (environment),
  2. createSliceServer({ seo: { origin } }),
  3. origin in seo.json,
  4. in development only: http://localhost:<port>,
  5. otherwise the server fails at startup.

Reading it from req.headers.host would produce one cached page per host and the wrong scheme behind a TLS proxy. In development the localhost fallback keeps the metadata inspectable; set SLICE_ORIGIN on a preview deploy so its canonical and its card point at the preview.

The sitemap is a committed file

slice seo sitemap writes src/public/sitemap.xml (and robots.txt only when the manifest has a robotsTxt block), from the indexable routes only. It never overwrites silently: an existing file that would change asks first, --yes skips the question, and a non-interactive run fails instead of waiting for input. An unchanged file is not rewritten.

Commit the result. slice seo check compares the committed file against the manifest and exits non-zero when they drifted, so the sitemap cannot rot between deploys.

Titles survive client-side navigation

Route entries accept metadata, and the router applies it on every navigation — including the first one — so the tab title does not stay on the landing page:

What it does and does not do:

  • only the fields the route declares; a route without metadata.title keeps the server's title,
  • canonical and robots are never written from the client: crawlers do not run your JavaScript,

so changing them there would only desync the SPA from the HTML that was served,

  • a router:change listener still wins, because the metadata is applied before the event fires,
  • slice doctor and slice seo check warn when routes.js and seo.json disagree on a title for the

same path — that disagreement is what would make the tab title change after hydration.

Put the canonical title in one place. If a route declares metadata.title, keep it identical to the manifest's (including the | Acme suffix), or let the manifest own the title and leave metadata.title out.

What this does not solve

  • The page body is still rendered in the browser. A crawler that does not execute JavaScript sees

the correct head and an empty #app. Pre-rendering the article content is a separate problem.

  • Generating the social image is not part of the runtime. The manifest accepts image, and

slice seo images produces the files from the real pages (it writes public/og/manifest.json, which you pass as seo.images). See [CLI commands](/Documentation/CLI#seo-images).

  • One language per route, for now. The manifest has no per-locale entries yet: with

[translator.routing](/Documentation/Translator) on, /en/... is still answered like an unknown path until the multilingual SEO phase ships. Apps without native SEO get the shell and translate in the browser.
