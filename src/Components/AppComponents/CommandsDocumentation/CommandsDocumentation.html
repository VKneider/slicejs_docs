Slice.js CLI

Overview

The Slice.js CLI (slice) helps you initialize projects, manage components, run the dev server, and maintain your toolchain. For project workflows, prefer package.json scripts (pnpm run ... or npm run ...) so execution is pinned to your local dependency tree.

Installation

When the slice launcher command is available (commonly after a global install that places slice in your PATH), it delegates to the nearest project-local node_modules/slicejs-cli from your current directory (including subdirectories). This keeps command execution aligned with the version pinned in each project.

Command Summary

slice build options

Source maps, hashed filenames & precompression

  • --sourcemap maps each minified bundle back to its readable pre-minified form, so production stack traces are debuggable. Off by default (source isn't shipped unless you opt in).
  • --hash-filenames names bundles by content hash for Cache-Control: immutable CDN caching. The runtime loads every bundle by the filename recorded in the bundle config, so hashing "just works" with no other change.
  • --compress writes a .gz and a brotli .br beside every text asset in dist/. slice start serves the precompressed variant per the client's Accept-Encoding (brotli preferred), instead of compressing on every request — a ~900&nbsp;KB bundle ships as ~100&nbsp;KB over the wire.

Reproducible builds

Set SOURCE_DATE_EPOCH (integer seconds since the Unix epoch) so the timestamps embedded in the bundle metadata/config are deterministic and a clean rebuild is byte-identical:

Unset, the current time is used.

Validation on build

Before bundling, slice build runs one validation pass over the project and blocks on anything that would ship a broken bundle:

  • sliceConfig combinations that build but misbehave (for example context.enabled with events.enabled off: ContextManager reactivity runs through EventManager, which is not bundled).
  • Component files that cannot be bundled: a syntax error, no default export while registered as a component, or an unresolved relative import.
  • A component registered in components.js whose file does not exist, or that points at a category with no paths.components entry, or whose category folder is missing. The runtime resolves <Category>/<Name>/<Name>.js, so none of those can load.
  • A reserved build directive (id, sliceId, singleton) declared in static props. The runtime strips it before setters run, so it is a silent no-op: pass it to slice.build(name, { id }) instead.
  • api/index.js with a syntax error. The server entry is not part of the bundle, but the deploy fails on it all the same.
  • src/routes.js with a syntax error or an unresolved relative import. That file is served as-is and loaded by the browser (it is not bundled), so a broken import stops the router from loading even though the bundle builds.
  • Static props with an unknown type, a schema on a non-object prop, an items on a non-array prop, or allowedValues that don't match the declared type.

Advisories are printed but do not block: a type: "any", a required prop without a default, a slice.build() of a name that is not registered, a component folder without its <Name>.js, a route whose component is not in components.js (it throws only when that route is visited), or a route written as :id instead of ${id} (Slice only compiles ${…} patterns, so a :param route is treated as a literal and never matches).

slice doctor reports the exact same classification in its Configuration and Components & Routes rows, because both commands run the same pass and the same helper decides what is blocking. Skip the component checks with --no-validate (not recommended); the sliceConfig and routes.js rules always run. See [Static Props](/Documentation/Static-Props) for the prop schema.

Doctor does not compile and does not boot the app: it cannot prove that esbuild resolves the whole graph, that dist/ is complete, or that the server starts. Use it as a fast first gate, then slice build, then run the app.

Exit codes

slice build exits 1 on a blocked build. slice doctor exits 1 when any row is a failure (it exits 0 when there are only warnings), so it can be used as a pre-deploy check: slice doctor && slice build.

init

Creates a new project folder and initializes it with the framework structure and the starter components from the official registry. Everything — package.json, node_modules, lockfile, src/, api/ — is created inside the new folder.

Options

What it does:

  • Creates the project folder and a package.json inside it (before any install, so

dependencies always anchor to the project folder).

  • Pins the chosen package manager in the packageManager field; later commands

(slice doctor) detects it from there or from the lockfile.

  • Installs slicejs-web-framework (dependency) and slicejs-cli (devDependency)

with the chosen package manager. Versions are not hard-pinned, so pnpm release-age policies (minimumReleaseAge) resolve cleanly.

  • Creates api/ and src/ structure from the framework base.
  • Installs the starter Visual and Service components from the registry.
  • Configures package scripts (dev, build, start, get, browse, sync, etc.).

dev

Starts the development server and serves from /src.

Options

Behavior

  • Ensures src/ and api/ exist (otherwise suggests slice init).
  • Falls back to port+1 if the requested port is busy.
  • Uses api/index.js with --development.

Import support scope

  • Supported: relative imports, bare npm packages (import 'pkg'), and absolute imports whose file exists under src/public/.
  • slice dev and slice build keep the same rule for preserved absolute (public/) imports.
  • See [External Dependencies](/Documentation/External-Dependencies) for npm packages.

start

Starts the production server and serves from /dist.

Options

Production serves static assets from src/public/ (copied into dist/) at the root URL — e.g. /Themes, /Styles, /images.

build

Builds production output by analyzing dependencies, generating bundles, and writing files to /dist.

Production builds include Structural framework components in bundles to avoid runtime fetches. These entries are stored as Framework/Structural/<ComponentName> in bundle config.

component create

Creates a new local component and registers it in components.js. Runs interactively, or non-interactively when you pass the name and category on the command line.

Only the missing pieces are prompted, so npm run component:create -- UserCard asks just for the category. Passing both runs with no prompts — useful for scripts and AI agents.

Rules:

  • Name must start with a letter and be alphanumeric.
  • Visual components get .js, .html, .css; Service components get .js only.
  • An invalid --category fails with a message listing the valid categories.

component list

Lists all local components by scanning category paths from sliceConfig.json and rewrites src/Components/components.js.

component delete

Deletes a local component and updates components.js. Interactive by default; pass the name, --category, and --yes to delete non-interactively.

get / registry get

Downloads components from the official registry (Visual or Service) into your project.

Options

Notes:

  • If no names are provided, the CLI opens an interactive selector.
  • Registry is fetched from the Slice docs repo.

browse / registry list

Lists available registry components.

sync / registry sync

Updates local Visual components to latest registry versions. Service components are detected but not updated automatically.

Options

doctor

Runs project diagnostics (structure, config, SEO, dependencies, components and routes, the server entry, external imports, port availability) and exits 1 when any row is a failure, so it works as a gate. Rows marked as warnings are advisory and exit 0.

Three rows cover what only a static check can see before a deploy:

  • Configuration validates sliceConfig.json against the framework's published

sliceConfig.schema.json (a string port is a pipe for listen(), a string "false" is truthy), and applies the same combination rules as the build.

  • Dependencies warns when the declared slicejs-web-framework range rejects the installed

version, or when the installed CLI requires a different one — the ^3.5.0-with-4.x case that shipped a broken install.

  • Server entry parses api/index.js; the build never executes it, so a syntax error there used to

reach production as a 500.

The Configuration and Components & Routes rows use the same rules as slice build: if the build would be blocked, doctor fails too, with the same message.

lint

Runs the project's ESLint with the config it declares. The CLI does not bundle ESLint: install it in the project (npm i -D eslint). slice lint is a thin wrapper so scripts and CI do not need to know the binary name.

The shared flat config ships with the CLI, so a project's config is one import:

It provides the browser environment plus the slice/Slice globals for src/, Node globals for api/, scripts/ and *.config.js, js.configs.recommended, a set of rules that warn rather than block, ignores for generated and vendored output (dist/, components.js, *.generated.js, .agents/, .claude/), and a Node/browser override for *.spec.js and tests/. Tooling that runs in Node imports nodeConfig instead:

Lint is for style and environment mistakes. Framework invariants — a component that cannot load, a broken route, a reserved prop, a prop the build rejects — are slice build / slice doctor rules and are not duplicated here, so the two can never drift.

Setting it up in an existing project

slice setup lint installs eslint and slicejs-cli as devDependencies when they are missing, writes eslint.config.js if the project has none, and adds lint / lint:fix scripts. It never overwrites a config or a script you already have, and --dry-run prints the plan without touching anything.

slice init does not install ESLint: the linter is a choice, and choosing it later is one command.

seo

seo sitemap

Writes src/public/sitemap.xml from seo.json, and robots.txt when the manifest has a robotsTxt block. Only indexable routes are listed; a ${param} route cannot be enumerated and never appears.

An existing file that would change asks first (default answer: no). A non-interactive run (CI) fails with a message naming --yes instead of waiting for input, and a file whose content is unchanged is never rewritten.

seo images

Renders the 1200×630 card each indexable route advertises, from the real page. It boots the app's api/index.js in development on a free port unless you pass --base-url.

It needs Playwright in the project (npm i -D playwright && npx playwright install chromium). The command writes <outDir>/manifest.json, which you pass as seo.images so the server merges the cards; seo.json itself is never edited (it is generated). Defaults for the card — theme, selector, template, outDir, budgetKB — live in the images block of seo.json.

seo check

Validates seo.json, cross-checks it against routes.js, and compares the committed sitemap with what the manifest would produce. Exits non-zero on any problem, so it belongs in CI.

See [SEO and Share Cards](/Documentation/Architecture/SEO) for the manifest fields and the origin rules.

version

Shows CLI version info and checks for updates.

help

Shows CLI help output.

types generate

Generates a TypeScript declaration file from your components' static props, so editors can autocomplete and type-check slice.build('Name', { ... }) calls.

Re-run it whenever you add or change component props. The output is generated — don't edit it by hand, and re-generate (or wire it into your build) to keep autocomplete in sync.

Best Practices

Prefer package scripts (pnpm run ... / npm run ...) for project commands.
Use npx slicejs-cli <command> for bootstrapping and recovery (for example before scripts exist).
Run npm run dev in one terminal and use another for component commands.

Gotchas

npm run sync only updates Visual components. Use npm run get -- <Service> --service --force for Service updates.
npm run component:list rewrites src/Components/components.js based on detected folders.
