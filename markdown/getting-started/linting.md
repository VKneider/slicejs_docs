# Linting

Slice ships an [ESLint](https://eslint.org) flat config with the CLI. One import gives a Slice project
the browser environment, the `slice`/`Slice` globals, a sane rule set, and ignores for generated
output — without every project inventing its own config.

Lint is for editor-time mistakes. It does **not** decide whether a project ships: that is
[`slice build`](/Documentation/CLI#build) and [`slice doctor`](/Documentation/CLI#doctor).

## Set it up

New to the project? One command installs ESLint, writes `eslint.config.js` (only if you do not have
one) and adds `lint` / `lint:fix` scripts:

```bash title="Existing project"
npm exec slice setup lint
```

```bash title="What it writes"
# package.json
"scripts": {
  "lint": "slice lint",
  "lint:fix": "slice lint --fix"
}
```

```js title="eslint.config.js"
import slice from 'slicejs-cli/eslint-config.js';

export default [...slice];
```

`slice setup lint --dry-run` prints the plan without touching anything. It never overwrites a config
or a script you already have, so running it twice is safe.

`slice init` does not install ESLint: the linter is a choice, and choosing it later is one command.

:::note
This requires a `slicejs-cli` that ships `eslint-config.js` (4.4 or newer). On an older CLI the import
fails; update the CLI first.
:::

## Run it

```bash
npm run lint              # the whole project
npm run lint:fix          # apply automatic fixes
npm exec slice lint src/Components   # a single path
```

`slice lint` runs the ESLint installed in your project — the CLI does not bundle it. If ESLint is
missing, the command says so and tells you how to install it. Any editor with ESLint support picks up
`eslint.config.js` on its own; no extra configuration.

## What the shared config provides

The default export is the **app preset**:

- `@eslint/js` recommended, as errors.
- Browser globals plus `slice` and `Slice` for `src/`.
- Node globals for `api/**`, `scripts/**` and `*.config.js` — the server side is Node, not browser.
- Node + browser globals (and Playwright's `page`/`browser`) for `*.spec.js`, `tests/**` and
  `playwright/**`.
- A small set of rules as **warnings**, so a long-green project does not turn red overnight
  (`no-unused-vars` with the `_` convention, `no-duplicate-imports`, `no-template-curly-in-string`, …).
- Ignores for `dist/`, `node_modules/`, `src/libs/`, `*.generated.js`, `src/Components/components.js`
  and the agent folders (`.agents/`, `.claude/`, `.opencode/`).

Tooling that runs in Node (a CLI, a build script) imports the other preset:

```js title="eslint.config.js (tooling)"
import { nodeConfig } from 'slicejs-cli/eslint-config.js';

export default nodeConfig;
```

App-specific globals go **after** the preset:

```js title="eslint.config.js (app globals)"
import slice from 'slicejs-cli/eslint-config.js';

export default [
  ...slice,
  { languageOptions: { globals: { ToastProvider: 'writable' } } },
];
```

## What lint does not do

Lint parses JavaScript. It has **no type information**: the shared config does not enable
`typescript-eslint`, there is no `tsconfig.json` in a Slice app, and the `.d.ts` generated by
`slice types generate` is read by your editor and by `tsc`, not by ESLint.

So "does lint take the types into account?" — no, and it should not: type-aware linting needs a
type-checking compiler and a much slower run for a JS-first framework. Type correctness lives
elsewhere:

| Question | Tool |
|---|---|
| Style, unused code, environment mistakes | `slice lint` |
| Contract of `static props`, generated types, component/route/config invariants | `slice build` / `slice doctor` |
| Do the generated declarations match my props? | `slice types generate` + `tsc --noEmit` |
| Does the app actually run? | `slice dev`, or a deployed preview |

That is why `slice lint` does not regenerate types: lint is read-only and fast, and writing files on
every lint would dirty CI and slow the editor. Keep `slice types generate` as its own step — for
example in the same CI job, right before `tsc --noEmit`.

Remember that the type generator reads the AST: `type`, `allowedValues`, `schema` and `items` must be
written literally. A constant is invisible to it and the prop falls back to `any` (see
[Static Props](/Documentation/Static-Props)). `slice types generate` warns when it finds one, and so do
`slice build` and `slice doctor`.

## In CI

```bash title="A complete static gate"
npm exec slice doctor
npm exec slice lint
npm exec slice build
```

`slice doctor` and `slice lint` exit 1 on failures; `doctor` rows marked as warnings (unscoped CSS, a
`destroy()` the framework never calls, an unregistered name in `slice.build`) exit 0. `slice build`
blocks on anything that would ship a broken bundle — see
[CLI](/Documentation/CLI#validation-on-build) for the exact split between lint, doctor and build.
